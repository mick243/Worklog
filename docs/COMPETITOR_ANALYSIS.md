## 0. 읽는 법

- 경쟁 서비스에 대한 사실은 모두 리서치 문서에서 가져왔어요. 괄호 안 숫자(예: "2.6")는 리서치 문서의 절 번호예요. cc-worklog 칸의 F·A·Q는 PRD, I-는 `docs/IMPROVEMENT.md` 항목이에요.
- 리서치가 "확인 못 함"으로 둔 것은 표에서 **?**로 뒀어요. 리서치에 아예 나오지 않는 것은 "리서치에 없음"으로 적었어요. 둘 다 없다는 뜻이 아니라 모른다는 뜻이에요. 판단에 필요한 것은 5장 "리서치 보강 필요"에 모았어요.
- 문서에서 읽은 사실이 아니라 거기서 미루어 본 판단에는 **(추정)**을 붙였어요.
- cc-worklog 칸은 **지금 구현된 것** 기준이에요(`docs/DEV.md` 10회차, `app/README.md`). PRD 초안에 들어갔지만 아직 구현되지 않은 A18~A22는 **예정(PRD 초안)**으로 따로 표시했어요(2.3).
- 표시: ○ 기준을 충족 · △ 일부만이거나 조건이 붙음 · × 없음(또는 공식 문서에 없음) · ? 리서치가 확인 못 함

## 3. 서비스별 강점·약점

cc-worklog의 강점·약점은 4장에 모았어요.

### 3.1 SpecStory

세션을 자동으로 마크다운에 남기고, 찾고, 이어 하게 하는 도구예요 (2.2).

강점
1. **넓은 지원과 쉬운 설치**: Claude Code를 포함한 터미널 에이전트 10개(목록에 "등"이 붙어 있어요)와 Cursor·Copilot IDE를 지원하고, Windows(PowerShell 5.1·7, x64·ARM64)·macOS·Linux 설치 스크립트와 Homebrew가 있어요 (2.2).
2. **자동 저장 + 지난 세션 내보내기 + 찾기·이어 하기**: `run`·`watch`가 쓰는 동안 자동으로 저장하고, `sync`가 SpecStory 없이 했던 세션도 `~/.claude/projects/`에서 읽어 마크다운으로 만들고, `search`·`resume`이 프로젝트·에이전트를 넘나들어요 (2.3).
3. **저장 시 비밀 가리기 기본 켜짐**: Betterleaks 규칙으로 저장하는 마크다운과 Cloud로 올리는 데이터를 함께 가려요 (2.6, v2.4.0 노트).
4. **사용 신호가 가장 커요**: 자체 집계 설치 232,326, 활성 사용자 11,513, 2026-10-18 릴리스 (2.7).

약점
1. **날짜별 정리·git 연동이 없어요**: 결과 단위가 세션마다 마크다운이고, 날짜별 정리와 git 연동은 CLI 문서에 나오지 않아요 (2.3). 업무일지로 쓰려면 사람이 다시 묶어야 해요 (추정).
2. **기본으로 나가는 것이 있어요**: CLI 익명 사용 통계가 기본 켜짐이고 확장은 PostHog로 이벤트를 보내요. Cloud를 쓰면 프롬프트와 답변 속 코드가 SpecStory로 가요 (2.6).
3. **가리기에 예외가 있고 기록이 프로젝트 폴더 안에 있어요**: `.specstory/cursorcloud/`에는 가리지 않은 기록이 있어 `.gitignore`를 넣어요(v2.16.0). 같은 회사가 `.specstory/history`를 커밋 전에 검사하는 별도 스킬(SpecStory Guard)을 둔 것은 기록이 저장소에 함께 커밋될 위험을 보여 줘요 (2.6, Guard는 [비공식 목록]) (추정).
4. **유료 쪽이 불투명해요**: Pro·Team 공식 가격을 확인 못 했고, 팀 협업이 지금 되는지 문서끼리 엇갈려요 (2.4, 2.5, 6).

cc-worklog와 겹치는 곳: 자동 삭제 전 기록 남기기(K5)와 저장 전 비밀 가리기(K4). 겹치지 않는 곳: git·날짜별 정리(K1, K3).

### 3.2 Entire

git 훅으로 에이전트 세션을 커밋 옆에 기록하는 도구예요 (3.2).

강점
1. **세션과 커밋을 가장 깊게 묶어요**: 커밋마다 대화·프롬프트·바뀐 파일·도구 호출·토큰을 체크포인트로 묶고, `blame`·`why`·`checkpoint explain`·되감기·`session resume`으로 코드가 왜 이렇게 쓰였는지 거슬러 가요 (3.3).
2. **비밀 가리기가 가장 두꺼워요**: 로컬 git에 쓰기 전에 9겹으로 검사하고, Betterleaks(수백 가지 형식)·goredact·PII(이메일·전화)·사용자 규칙 묶음 폴더까지 있어요 (3.6).
3. **기간 요약이 이미 있어요**: `recap`(오늘·주·월·90일, 나·팀), `dispatch`(기본 7일 공유용 마크다운), `activity`(entire.io, 한 달) (3.3).
4. **자원과 속도**: 별 5.2k, 커밋 10,685, 2026-10-20 안정판·10-21 야간판, 전 GitHub CEO와 6천만 달러 시드 투자 (3.2, 3.7).

약점
1. **기록이 저장소 안에 있고 기본으로 원격에 올라가요**: 체크포인트는 내 git 저장소 안에 있고 `push_sessions` 기본 `true`라 `git push` 때 함께 올라가요. 저장소를 읽을 수 있는 사람은 체크포인트도 읽고, 공개 저장소면 공개돼요 (3.6).
2. **가리기 빈틈을 스스로 적어요**: best-effort이고, 원본 세션 파일·작업 트리 스냅숏(shadow branch)·진단 로그는 가리지 않으며, 사용자 이름·파일 경로는 PII 범주에 없어요. `import`한 기록에 가리기가 적용되는지는 ? (3.6, 6)
3. **여러 저장소는 계정 쪽이에요**: 로컬은 저장소마다 `entire enable`이고, 여러 저장소 검색·`dispatch` 클라우드 모드·`activity`는 entire.io 계정이 있어야 해요. entire.io 요금은 ? (3.3, 3.4)
4. **요약에 모델을 써요**: `checkpoint explain --generate`·`dispatch --local`은 에이전트 CLI(기본 Claude Code)로 글을 써서 모델 사용량이 들고, 가리고 줄인 대화를 요약 제공자로 보내요 (3.4, 3.6).

cc-worklog와 겹치는 곳: 세션+커밋(K1), 쓰기 전 가리기(K4), 기록 남기기(K5), 기간 요약(K3 기간). 겹치지 않는 곳: 저장소 밖·네트워크 0(K6), 경로 속 사용자 이름 가리기(K4), 로그인 없이 여러 저장소 하루 일지(K2·K3 하루, 단 `recap` 세부 ?).

### 3.3 receipts

Claude Code 세션 기록과 로컬 git 기록으로 기간 영향 보고서를 만드는 Anthropic 공식 플러그인이에요 (4.1, 4.2).

강점
1. **Anthropic 공식**: 마켓 작성자 Anthropic, `/plugins`(Anthropic 내부 개발), claude.com "Anthropic verified"예요 (4.1). Claude Code 사용자에게 가장 먼저 눈에 띄고 믿기 쉬운 자리예요 (추정).
2. **보내는 것이 아주 적어요**: 기록 분석은 로컬 스크립트이고 네트워크 호출이 없으며, 모델에는 집계 JSON만 한 번 가요. 코드·대화·도구 이름은 안 보내고 이메일은 로컬에서만 써요 (4.4, 4.6).
3. **설치가 쉽고 결과물이 보고용이에요**: `/plugin install` 한 줄, 무료, md·html(Export CSV, PDF 인쇄)을 만들고, 매니저에게 과장 없이 설명하는 문구를 함께 줘요 (4.2, 4.3).
4. **세션과 git을 함께, 여러 저장소를 프로젝트별로**: Claude가 손댄 파일로 거른 커밋과 줄 수를 프로젝트별로 세요 (4.3, 4.6).

약점
1. **하루별이 없어요**: 결과는 기간 합계와 프로젝트별 합계이고, 활동한 날은 수로만 나와요 (4.3).
2. **보관·가리기가 없어요**: 지금 남은 `.jsonl`만 읽고, 비밀 가리기 대신 내용을 저장하지 않는 방식이에요 (4.6). 30일이 지나면 그 기간은 보고서에서도 사라져요 (추정).
3. **세는 방식의 한계**: PR 수는 `gh pr create` 명령 수라 실제 PR인지 확인하지 않고, 세션이 닿지 않은 저장소와 Claude가 손대지 않은 파일의 커밋은 보지 않아요 (4.3, 4.6).
4. **쓰는 사람이 아직 적어요**: claude.com 설치 195, 버전 번호 없음, Windows 동작 ? (4.7, 6).

cc-worklog와 겹치는 곳: 세션+git·여러 저장소(K1·K2, 수로만), 로컬 처리(K6). 겹치지 않는 곳: 하루 단위(K3), 가리기(K4), 보관(K5), 손으로 한 커밋.

## 4. cc-worklog의 위치

**이제 빈자리가 아닌 것**
- 비밀 가리기 그 자체: SpecStory·Entire 모두 저장 전에 기본으로 가려요 (2.6, 3.6).
- 30일 뒤에도 기록을 남기는 것 그 자체: SpecStory `watch`·Entire 훅이 자동으로 남겨요 (2.3, 3.3). cc-worklog는 실행할 때만이라 이 칸은 오히려 뒤져요.
- 세션과 커밋을 함께 보는 것 그 자체: Entire가 더 깊어요 (3.3).
- 기간 요약: Entire `recap`·`dispatch`, receipts가 있어요 (3.3, 4.3).

**아직 cc-worklog에만 있는 것 (지킬 차별점)**
1. **하루 단위 × 프로젝트별로, 세션과 여러 저장소의 실제 커밋을 한 파일에**: 세 서비스 중 확인된 곳이 없어요. 세션이 없던 저장소의 커밋(`roots`)과 Claude가 손대지 않은 내 커밋도 들어가요. receipts는 Claude가 손댄 파일 경로로 거르고 세션 없는 저장소는 안 봐요 (4.6). Entire `recap`이 어디까지 하는지는 ?라 이 차별점은 잠정이에요.
2. **저장소 밖, 내 컴퓨터에만, AI·네트워크 0**: Entire는 체크포인트를 저장소 안에 두고 기본으로 push하며 요약에 모델을 써요 (3.4, 3.6). SpecStory는 프로젝트 폴더 안에 쓰고 통계가 기본 켜짐이에요 (2.6). cc-worklog는 데이터 폴더 한 곳에만 쓰고 네트워크 요청이 0건이에요 (PRD 5장).
3. **결과물 검사와 나중에 다시 가리기, 경로 속 사용자 이름 가리기**: `check`(통과·실패 종료 코드)와 `redact`(나중에 더한 패턴을 이미 저장한 보관본·일지에 적용)는 리서치에서 경쟁 서비스의 같은 기능이 나오지 않았어요(없다는 확인은 아니에요, 5장). 경로 속 사용자 이름은 Entire PII 범주에 없다고 리서치에 적혀 있어요 (3.6). SpecStory Guard(커밋 전 검사)는 검사 쪽과 일부 겹쳐요 (2.6).
4. **삭제 예상일·삭제 임박 표시**: 보관 상태와 삭제 예상일을 화면·실행 요약에 보여 주는 기능은 리서치에 경쟁 서비스 쪽 이야기가 없어요 (F3, A9).

### 4.4 cc-worklog의 약점 (경쟁 대비)

1. **성숙도가 없어요** (K8): 배포 전이라 사용자가 없고 1인 프로젝트예요. SpecStory 설치 232,326, Entire 별 5.2k, receipts는 Anthropic 공식이에요 (2.7, 3.7, 4.1). 실제 기록 시험도 한 사람 기록으로 한 번뿐이에요 (A17).
2. **기록이 자동으로 남지 않아요** (K5): 보관이 일지 만들기·`archive` 실행에 달려 있어서 실행을 잊으면 30일 뒤 지워져요 (A8, I-22). SpecStory `watch`와 Entire 훅은 따로 실행하지 않아도 남겨요 (2.3, 3.3). PRD 문제 3을 푸는 핵심 기능(F3)인데 이 점에서는 경쟁 도구가 앞서요.
3. **주간·기간 정리와 문장 요약이 없어요** (K3): 타깃이 주간 보고·회고인데 하루 단위뿐이고(I-23), 결과는 요청 원문 앞부분과 커밋 목록이에요(I-26). receipts는 매니저용 설명 문구를, Entire `dispatch`는 공유용 마크다운을 만들어요 (4.3, 3.3). "AI 없음"이 강점이면서 이 약점의 까닭이기도 해요.
4. **가리기 규칙 폭이 좁아요** (K4): 내장 규칙이 19개예요(DEV). Entire 문서는 Betterleaks를 "수백 가지 형식"으로 적어요 (3.6). 그래서 형식이 알려진 비밀도 cc-worklog가 더 많이 놓칠 수 있어요 (추정). 이메일 말고 전화번호 같은 PII도 다루지 않아요.
5. **지원 범위가 좁아요** (K7): Claude Code 기록만, CLI·화면 문구는 한국어만(A1), Windows 11에서만 돌려 봤고(I-19), npm에 아직 없어요(I-08). SpecStory·Entire는 에이전트 9~10개와 세 OS를 지원해요 (2.2, 3.2).
6. **지금 구현에 구멍이 있어요**: `check`가 이름·이메일을 가리지 않은 일지를 통과로 끝내고(I-01), 세션 없는 저장소의 커밋이 말없이 빠지고(I-02), 공개용 일지가 다음 기본 실행에서 되돌아가고(I-03), 손으로 적은 메모를 덮어써요(I-04). 모두 예정(PRD 초안, A18~A21)으로 메워질 것이지만 아직은 차별점 2·3을 약하게 해요.
7. **일부러 뺀 기능이 비교 표에서는 빈칸이에요**: 검색·이어 하기·blame·공유·팀 보기는 PRD가 범위 밖으로 뒀어요 (PRD 3장). SpecStory·Entire와 나란히 놓으면 기능이 적어 보여요 (추정).

### 4.5 시사점

1. **README 비교 표와 PRD 2장을 리서치에 맞게 고치고, 차별점을 다시 적기.** 표 기준 날짜를 2026-10-21로 바꾸고, SpecStory는 "저장 시 비밀 가리기 기본, 날짜별·git 결합 없음", Entire는 "커밋 단위 체크포인트 + `recap`·`dispatch` 기간 요약, 로컬 git에 쓰기 전 가림, 기본으로 push", receipts는 "기간 집계, 가리기·보관 없음"으로 적어요. 차별점은 "가리기·보관"이 아니라 4.2의 네 가지(하루·프로젝트별 한 파일, 저장소 밖·네트워크 0, `check`·`redact`·경로 속 사용자 이름, 삭제 예상일)로 좁혀 적고, cc-worklog가 뒤지는 칸(자동 기록, 기간 요약, 성숙도)도 표에 정직하게 둬요. PRD는 planner, README는 개발 쪽 몫이에요.
2. **다음 후보 1순위로 자동 보관의 가벼운 형태(I-22)를 보기.** 경쟁 대비 가장 큰 차이가 "실행을 잊으면 지워짐"이에요. 자동 등록이 어렵다면 S3에 "다음 삭제 예상일이 가장 빠른 세션" 한 줄, 첫 실행 때 등록 방법 안내부터 넣을 수 있어요. 훅으로 한다면 PRD 5장의 `SessionEnd` 1.5초 제한 안에서 해야 해요.
3. **A18 위에 주간·기간 묶음을 AI 없이 얹기(I-23).** 타깃(주간 보고·회고)에 바로 닿고, Entire `recap --week`·`dispatch`, receipts `week`와 나란히 설 칸이에요. receipts처럼 집계 위주로, 과장 없이 수와 목록으로 만들면 "AI 0" 원칙을 지키면서 문장 요약이 없는 약점(I-26)도 일부 덜어요 (추정).
4. **차별점을 먼저 굳히기.** A19(`check`의 이름·이메일 알림)와 A20은 차별점 2·3을 직접 지키는 일이라 예정 기능 중 먼저 구현할 만해요. 가리기 규칙 폭은 Betterleaks 규칙 모음을 참고할 수 있지만, PRD 5장대로 라이선스를 확인한 뒤에만 가져와요(리서치 보강 필요).
