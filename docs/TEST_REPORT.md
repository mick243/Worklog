- **브라우저 콘솔 오류: 0건이에요.** 화면(S1·S2)을 열 때와 링크를 누를 때 모두 오류·경고가 없었어요. 화면에 스크립트가 하나도 없는 구조라서(`document.scripts.length` = 0) 콘솔에 남는 메시지 자체가 없었어요.
- **로그인 화면이나 보안 문자는 나오지 않았어요.** 같은 화면에서 3번 이상 막힌 곳도 없어요.
- **되돌릴 수 없는 버튼은 누르지 않았어요.** 화면에는 버튼이 없고 읽기 전용이에요. 터미널의 `redact`(다시 가리기)는 이번에 만든 가짜 데이터에만 실행했어요.

## 어떻게 실행했나

- **localhost:4000:** 원래 그 주소에서 도는 것이 없었어요. 그래서 cc-worklog의 로컬 화면(`cc-worklog view --port 4000`)을 가짜 데이터로 띄우고 Chrome으로 열었어요. 빈 화면 확인용으로 4002번에도 하나 더 띄웠어요. 둘 다 끝난 뒤 껐어요.
- **가짜 사용자 환경:** 임시 폴더에 가짜 홈을 만들고 그 안에 세션 기록과 git 저장소를 넣었어요. 저장소 4곳(하위 폴더·다른 사람 커밋 포함), 저장소가 아닌 폴더, 사흘에 걸친 세션, `ai-title`만 있는 세션, 비밀 값과 사내 토큰, 모르는 줄과 깨진 줄, 25일 전 세션이 들어 있어요. 터미널 명령은 처음 쓰는 사용자처럼 옵션 없이 `cc-worklog`부터 실행했어요.
- **사용자의 실제 세션 기록·저장소·`~/.cc-worklog`는 쓰지 않았어요.** 끝난 뒤 가짜 데이터, 임시 서버 설정, 잠금 파일을 모두 지웠고 남은 것이 없는 것도 확인했어요.
- **확인 방법 표기**
  - 터미널: 명령을 직접 실행해서 출력과 파일을 확인했어요.
  - Chrome: localhost 화면을 Chrome에서 직접 열고 눌러 봤어요.
  - 앱 브라우저: Chrome 창 크기가 바뀌지 않아서, 좁은 화면만 앱 안 브라우저의 모바일 크기(375px) 흉내로 봤어요.
  - 자동 시험: 실제 터미널 키 입력이나 강제 종료처럼 손으로 재현하기 어려운 것은 자동 시험(`npm test`, 72개 모두 통과)의 해당 시험으로 판정했어요.

### F1-08 지운 워크트리의 세션이 원래 저장소로 묶이지 않아요 (`--root`를 안 줬을 때)

- **기대:** 지워진 워크트리의 세션이 원래 저장소 `api`로 묶여요(PRD A4).
- **실제:** 세션이 "저장소 없음" 묶음에 들어갔어요. 똑같이 `--root <work 폴더>`를 주면 `api`로 제대로 묶였어요. 그래서 원래 저장소를 `--root`로 알려 줘야만 동작해요. PRD A4에는 그런 조건이 없어요.

### F1-20 `--root`에 없는 폴더나 파일 경로를 줘도 아무 알림이 없어요 (기대 동작)

- **한 일:** `cc-worklog --root <없는 폴더>`, `cc-worklog --root <파일 경로>`를 실행했어요.
- **기대:** 멈추지 않고, 그 경로를 건너뛴다고 알려요. PRD에는 정해져 있지 않아서 계획에 "(기대 동작)"으로 적었던 항목이에요.
- **실제:** 멈추지 않고 나머지 일지는 잘 만들어요(종료 코드 0). 하지만 잘못 준 경로에 대해서는 아무 말이 없어요. 오타를 내면 그 저장소 커밋이 왜 빠졌는지 알 길이 없어요.
- **스크린샷:** 터미널 출력이라 없어요. 출력의 `읽음` 줄은 `--root`를 주지 않았을 때와 같았어요(저장소 2개).

### F1-21 쓰는 중인 포트로 화면을 열면 말없이 다른 포트로 열어요 (기대 동작)

- **한 일:** 4000번에 화면 서버가 이미 떠 있는 상태에서 `cc-worklog view --port 4000`을 한 번 더 실행했어요.
- **기대:** 4000번이 쓰이는 중이라고 알리고 다른 포트를 고르라고 안내해요. 이것도 "(기대 동작)" 항목이에요.
- **실제:** `로컬 화면을 열었어요: http://127.0.0.1:4001/`만 나오고 4001번으로 열렸어요. 4000번이 쓰이는 중이었다는 말은 없어요. 주소를 보지 않고 `localhost:4000`을 다시 열면 앞서 띄운 다른 서버(다른 데이터 폴더일 수 있음)를 보게 돼요.
- 참고: 범위 밖 포트(`--port 99999`)는 사용법 오류(종료 코드 1)로 제대로 막혔어요.
- **스크린샷:** 터미널 출력이라 없어요.

### F2-23 다른 프로그램이 일지 파일을 잡고 있으면 다시 가리기가 그 파일을 말없이 건너뛰고 "완료"로 끝나요

- **한 일:**
  1. 사용자 패턴을 새로 더했어요(10-19 일지의 커밋 문구 "헤더 정리"에 맞는 패턴).
  2. `2026-10-19.md`를 다른 프로그램이 연 것처럼 잠갔어요(Windows 공유 없음 모드).
  3. 그 상태에서 `cc-worklog redact --yes`를 실행했어요.
  4. 잠금을 푼 뒤 `archive`, `check`, `redact`를 차례로 실행했어요.
- **기대:** `.md`도 바뀔 파일 목록에 나와요. 읽거나 쓰지 못하면 `[실패]`나 `[경고]`로 알리고, 다음 실행이 마저 끝내요.
- **실제:**
  - 잠긴 `.md`가 바뀔 파일 목록에서 **말없이 빠졌어요.** 화면용 `.json`만 다시 썼는데 결과는 `다시 씀 일지 1개`, 종료 코드 0이었어요. 경고는 없었어요.
  - 그래서 화면(S2)은 `[가림:헤더 문구]`로 가려졌는데, 같은 날 마크다운 파일 25번째 줄에는 원문이 그대로 남았어요. 화면과 마크다운이 서로 달라졌어요.
  - 잠금을 푼 뒤 `check`는 남은 의심 1건(마크다운 25번째 줄)으로 실패했어요.
  - 그런데 `redact`를 다시 하면 "바뀔 자리 0개"와 "다시 가리기로 고칠 수 없는 의심 1건" `[알림]`만 나오고 고치지 못했어요.
  - 그 날짜 일지를 다시 만들어야(`cc-worklog --date 2026-10-19`) 해결됐어요. 이 방법은 어디에도 안내되지 않았어요.

- 참고: 계획은 "확정 뒤 이름을 바꾸는 순간" 잠기는 경우였어요. 그 순간을 맞추기 어려워 실행 전부터 잠가 두는 쪽으로 바꿨고, 그러다 위 문제가 나왔어요. 이름을 바꾸는 순간의 EBUSY 자체는 재현하지 못했어요.

### 계획 밖 추가 발견 X-01 BOM이 붙은 설정 파일을 "올바른 JSON이 아니에요"로 거절해요

- **한 일:** 내용은 올바른데 맨 앞에 UTF-8 BOM이 붙은 `patterns.json`과 `config.json`으로 `cc-worklog check`를 실행했어요. Windows PowerShell 5.1의 `Out-File -Encoding utf8`처럼 BOM을 붙여 저장하는 도구가 흔해요. 실제로 시험 준비 중 PowerShell로 패턴 파일을 고쳤다가 이 상황을 처음 만났어요.
- **기대:** BOM을 무시하고 읽어요.
- **실제:** `[실패] 사용자 패턴 파일을 읽지 못했어요 (올바른 JSON이 아니에요)` 또는 `[실패] 설정 파일이 올바른 JSON이 아니에요`로 멈춰요(종료 코드 1). 파일을 열어 봐도 틀린 곳이 보이지 않아서, 처음 쓰는 Windows 사용자는 원인을 찾기 어려워요.
- **스크린샷:** 터미널 출력이라 없어요.

## 브라우저 콘솔 확인

연 페이지는 아래와 같고, 모두 콘솔 오류·경고가 0건이었어요.

- `localhost:4000/` (S1): 처음 열 때, 새로 고침, 배너가 있는 상태
- `localhost:4000/day/2026-10-20`, `/day/2026-10-19`, `/day/2026-10-16`, `/day/2026-10-15` (S2): 날짜 클릭, 목차 클릭, 이전·다음 날짜 클릭
- `localhost:4002/` (빈 S1), `/day/2099-01-01` (없는 날짜)

없는 주소(`/etc`, `/day/abc`, `/day/2026-13-40`, 경로를 거슬러 올라가는 주소)는 모두 404 "없는 화면이에요"였어요.

## 그 밖에 본 것 (실패는 아니에요)

- **F2-24 시나리오 기준을 고쳐야 해요:** 잘린 자리에 걸친 값은 패턴과 맞지 않아서 처음부터 의심으로 잡히지 않아요. 그래서 "[알림]이 나와요"라는 기준은 맞지 않아요. 잘림이 비밀 값 중간에 걸리면(예: `CORP-998…`) 앞자리 일부가 일지에 보일 수 있고, 검사도 그걸 잡지 못해요. 그 날짜 일지를 다시 만들면 사라지는 것은 확인했어요.
- **보관에 실패한 세션의 날짜:** 처음부터 읽지 못한 세션 파일은 날짜를 알 수 없어서, 실제로는 10-19 세션이어도 S1에 "일지가 없는 날짜의 보관 실패 세션"으로 세요. 이미 보관한 적 있는 세션이 실패하면 그 날짜 행에 "보관 실패"가 제대로 붙어요.
- **같은 날 다시 만들 때 옵션:** `--root`를 준 날과 안 준 날의 일지가 달라요. 처음 쓰는 사용자가 저녁에 옵션 없이 다시 만들면, 낮에 `--root`로 넣었던 저장소가 그날 일지에서 빠져요. 자주 쓰는 `--root`는 `config.json`의 `roots`에 두라고 README에서 안내하면 좋아요.
- **자동 시험이 이 컴퓨터의 시간대에 기대요:** 이 컴퓨터의 Node는 `TZ` 환경 변수를 무시하고 Windows 시간대(서울)를 써요. 시험 도우미가 `TZ=Asia/Seoul`을 넣어도 효과가 없어서, 다른 시간대 컴퓨터에서는 날짜 경계 시험이 다르게 나올 수 있어요.
- **Chrome 창 크기:** Chrome 창이 최대화돼 있어서 창 크기 바꾸기가 먹지 않았어요. 좁은 화면은 앱 안 브라우저로 대신 봤어요.
